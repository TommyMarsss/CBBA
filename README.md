# CBBA：基于拍卖共识的多机器人任务分配

用 Go 标准库实现的 **CBBA（Consensus-Based Bundle Algorithm）** 分布式任务分配算法，
附带同步轮次模拟器（支持通信丢包）、分配结果校验器，以及一个完全自包含的
静态 HTML 回放报告（原生 HTML/CSS/JavaScript，无任何框架与外部依赖）。

## 快速开始

```bash
# 运行测试
go test ./...

# 运行一次分配并生成静态回放报告 report.html（浏览器直接打开即可）
go run ./cmd/cbba -robots 6 -tasks 14 -seed 42 -loss 0.4 -loss-rounds 6 -out report.html
```

报告文件内嵌全部数据与逻辑，不启动任何服务、不加载任何外部资源。打开后可逐轮
回放竞价与共识过程，冲突任务（多方认领）以红色高亮、丢包与让位事件在侧栏列出。

## 拍卖协议

### 评分与出价

- 每个任务 `j` 有位置与收益 `Reward`；每个机器人有位置、任务包容量 `Capacity`
  与行程预算 `MaxTravel`。
- 机器人 `i` 对任务 `j` 的出价为**边际插入收益**：
  `bid = Reward_j − λ · (插入 j 后路径长度的增量)`，插入位置取使增量最小的那一处。
  只有 `bid > 0` 且不超出行程预算时才会出价。
- 每个机器人维护一个**有序任务包**（bundle），每轮贪心地把当前最高正收益且能
  赢得的任务插入包中，直到容量耗尽或无可出价任务。

### 冲突仲裁规则（确定性）

对同一任务的两份出价 `(bid, robotID)`：

1. **出价高者胜**；
2. 出价相同（在 `1e-9` 容差内）时，**机器人 ID 小者胜**。

该规则是全序的：所有机器人看到同一对出价时必然得出相同结论，因此不会出现
"两个机器人都认为自己赢得同一任务"的终态。

### 共识阶段

每轮各机器人广播三元组向量（对应原论文的 `y / z / s`）：

- `y[j]`：我所知的任务 `j` 的当前最高出价；
- `z[j]`：我所知的任务 `j` 的胜者（无胜者时缺省）；
- `s[r]`：我最新收到机器人 `r` 信息的轮次（时间戳）。

接收方按发送者对任务 `j` 的四种主张分别处理（`k` 为发送者）：

| 发送者主张 | 处理 |
|---|---|
| `z_kj = k`（自荐） | 若我也认为 `k` 胜：仅当消息比我知道的更新（时间戳）才接受（允许胜者自我修正出价）；否则按仲裁规则比较 |
| `z_kj = i`（认为我胜） | 仅当发送者是在撤回它自己的主张（我此前认为 `k` 胜）时重置；其余忽略——我自己的出价本地计算，不采纳过期的"你赢了" |
| `z_kj = 无`（释放） | 只有当我认为胜者恰是发送者时才重置（只有胜者本人能释放任务） |
| `z_kj = m`（第三方胜） | 发送者撤回自己旧主张时无条件跟随；其余第三方主张**仅当发送者关于胜者的信息比我更新**（`s_k[m] > s_i[m]`）才采纳，再按仲裁规则比较 |

此外：

- **级联剪枝**：失去任务包中某一任务后，其后的所有任务一并移除（它们的边际
  出价是基于已不存在的路径计算的），下一轮重新竞价。
- **过期主张释放**：若机器人认为自己赢得任务 `j` 但 `j` 不在其任务包中（容量
  已满或已无正收益插入位置），它必须释放该主张并广播，否则该任务会被永久
  阻塞（其他机器人因仲裁规则不会出价）。

## 收敛性保证

**无丢包时**：每次任务易主都要求新出价严格高于记录的旧出价（平局仅按 ID 仲裁
一次），而出价集合有限（由有限的任务包组合决定），因此易主次数有限；时间戳
门控保证过期信息只能被丢弃、不能复活（这是实现中最关键的一条：没有它，被
重置的过期主张会被第三方中继无限复活，信念在两个值之间永振荡——本仓库的
测试在 20+ 机器人规模下复现并验证了该修复）。状态不再变化即收敛。

**丢包时**：丢包只会延迟信息传播，不会破坏上述单调性。丢包窗口结束后，系统
等价于从一个合法的中间信念状态继续做无丢包共识，因此在有限轮内收敛到与
无丢包情形一致的无冲突分配（见 `TestConvergesAfterBlackout`：丢包场景与无
丢包场景的最终分配逐任务一致，且丢包场景需要更多轮次）。

**收敛判定**：一整轮中没有任何机器人改变状态、且没有任何消息被丢弃，即判定
收敛。`MaxRounds` 为安全上限，达到上限仍未收敛会明确标记 `Converged=false`，
不会假装成功。

## 结果校验（无冲突性、完整性）

`Validate` 对最终分配做三项检查：

1. **无冲突**：任意非协作任务不得出现在两个机器人的任务包中（协作任务
   `Coop: true` 允许多机器人共同承接，豁免检查）；
2. **无法承接的任务明确报告**：对每个未分配任务，检查是否存在至少一个机器人
   能以正收益单独承接（空任务包插入）。不存在 → 列入 `Unassignable` 并明确
   报告，绝不静默丢弃；
3. **完整性**：可承接但未分配的任务列入 `Unassigned`（容量或边际收益原因），
   同样明确报告。每个任务必然属于"已分配 / 无法承接 / 未分配"三类之一。

## 已知局限

- **同步轮次模型**：模拟器按轮同步执行"竞价 → 广播 → 接收"，真实异步部署需要
  额外的消息排序与超时机制；但共识规则本身不依赖同步性（时间戳门控是逐消息的）。
- **全连接广播**：每轮所有机器人两两通信。稀疏拓扑下算法结构不变，只是收敛
  更慢（信息多跳传播）。
- **贪心启发式**：CBBA 保证无冲突与收敛，不保证全局最优。可能出现"某任务单独
  看可承接，但对所有机器人的当前路径边际收益均非正"而未被分配的情形——此时
  会被列入 `Unassigned` 明确报告（理论上有 ≥50% 的最优性保证，见原论文）。
- **协作任务是简化模型**：仅豁免冲突检查，未实现真正的多机器人协同时序。
- **丢包模型**：按轮次窗口模拟（`RandomLoss` / `BlackoutLoss`），窗口外信道
  理想。若丢包永不停止，算法不保证收敛（与任何共识协议一致），但已达成的
  无冲突性不会被破坏——丢包只会延迟收敛，不会制造冲突。

## 项目结构

```
cbba/            核心库
  types.go       任务/机器人定义与仲裁规则
  agent.go       单机器人：竞价（阶段一）与共识（阶段二）
  sim.go         同步轮次模拟器、丢包模型、收敛检测、事件日志
  validate.go    分配结果校验（无冲突/无法承接/完整性）
  report.go      自包含静态 HTML 回放报告生成
  *_test.go      自动化测试
cmd/cbba/        命令行演示：运行一次分配并输出 report.html
```

## 测试覆盖

- `TestHigherBidWins` / `TestTieBreakByRobotID`：竞价冲突按规则正确仲裁；
- `TestConvergesAfterBlackout` / `TestConvergesUnderRandomLoss`：全丢与随机丢包
  后仍收敛到与无丢包一致的无冲突分配；
- `TestUnassignableTaskReported`：无法承接的任务被明确报告而非丢弃；
- `TestLargeScaleConflictFree`：40 机器人 × 150 任务 + 丢包窗口下收敛，结果
  满足无冲突、容量约束，且每个任务都有明确去向；
- `TestCooperativeTaskExemptFromConflicts`：协作任务的多机器人承接不计冲突；
- `TestValidateDetectsConflict` / `TestWriteReportSelfContained`：校验器与报告
  生成器自身的行为。
